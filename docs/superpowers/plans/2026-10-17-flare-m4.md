## Global Constraints

Copied from the roadmap, M2 and M3; every task obeys them.

  in an identifier, path, key or string (README and docs may name Prism Terminal as the source). The `--p-*`
  token names are Prism Terminal's CSS variables; in Flare they appear only as strings in `flare-theme`'s
  token table and in test fixtures (the Slint properties drop the `--p-` prefix).
- **Every display scaling works** (roadmap, owner 2026-10-17: 100, 125, 150, 175, 200, 225, 250 and 300

  theme at 100, 150 and 225 on both grid painters (Task 30); a theme or material change at a fractional
  scale never moves a cell (the grid is refitted only by a font change).

- Nothing in tests may open a visible window, take the foreground, touch the real clipboard or the real
  `%APPDATA%\Flare`. The ONE exception is Task 19's material spike, run by the orchestrator with the owner told
  first (see that task). UI tests use the headless software platform only.
- New dependency = a reason line in `README.md` and a `THIRD-PARTY-NOTICES.md` entry in the same PR; this

**Floating point.** Probed with rustc on this PC against V8 for every 8-bit channel (`ORACLE\ulp2.rs`,
`ulp2.mjs`): Rust's `f64::powf` equals `Math.pow` bit for bit except 2 of 1,024 values (1 ulp); Rust's `cbrt`
differs from `Math.cbrt` on 85 of 256 values (the OKLab path: sidebar ground, accent lift, wall order). A
difference of 1 ulp can only move a rounded byte when a value sits within 1e-15 of `x.5`; none of the
fixtures' values does in the oracle run, and PT's own tests are ranges and orderings. Policy: fixtures
compare exact strings; if one differs by 1 in one channel, the builder reports it (with the input and both
outputs) and the orchestrator decides; nobody edits an expected value or the algorithm.
JavaScript `Math.round` rounds ties toward +infinity; Rust's `round` rounds ties away from zero. Every PT
call rounds a non-negative number, so they agree, but `num::js_round` (Task 1) is used everywhere PT says
`Math.round`, and PT's seeded generator in `termAnsi.test` (`seed * 1103515245` overflows 2^53) is reproduced
with `f64` arithmetic, which gives the identical sequence.

## Decisions taken by the planner (not the owner)

D1. **Fixtures come from PT's code, not from hand-typed numbers.** The oracle (Task 2) is committed under
   `tools/oracle/` with its output under `crates/flare-theme/tests/fixtures/`; the Rust tests compare exact
   strings. `presets_data.rs` and `fonts_data.rs` are GENERATED from it (so no hex value in the 39 themes or
   the 15 faces is ever typed by a builder), and both say so in their first line.
D2. **`flare-theme` is pure and depends on nothing**, so `flare-render` does not depend on it either: the
   conversion from a `TermTheme` to the renderer's `Palette` lives in the binary (`chrome_apply::palette_of`).
D3. **All of PT's `colour.test.ts` ports into `flare-theme`**, including `colourCommit`, `alphaPct` and
   `snapAlphaStep` (the ledger said `flare-settings`): one test file ported whole, in the crate that owns the
   maths; M7's picker calls them. Task 32 updates the ledger rows. `seeThrough.test` also ports here (the
   default levels feed `ground_alpha`); the PT-import migrations (`opacityMigration`, `seeThroughMigration`),
   `colourFormat` and `termPrefs` stay in M7 with the import.
D4. **The ground is painted by the UI when the window is see-through** (PT's `paintsGround`): the grid image is
   clear where the theme's ground is and the Slint `Theme.ground` rectangle behind it carries the alpha once,
   so there is never a second coat. At 100% (the default) the grid keeps painting its own opaque ground
   exactly as M1 and M2 do. The grid image is declared premultiplied (`Image::from_rgba8_premultiplied`) in
   both modes: at alpha 255 premultiplied and straight are the same bytes.
D5. **See-through needs the GPU renderer.** The software renderer's presenter has no alpha (Verified facts), so
   with `--renderer software` (or after a GPU fallback) the window stays solid, the slider's value is kept,
   and Settings (M7) reads "Needs the graphics renderer." This is owner question Q1.
D6. **Two Windows gates.** `acrylic_ok(build >= 22000)` is PT's rule and its tests port unchanged (it decides
   whether the row is "Windows 11"). `system_backdrop_ok(build >= 22621)` is what lets Flare make the DWM
   call, because `DWMWA_SYSTEMBACKDROP_TYPE` does not exist before it. On builds 22000 to 22620 the row reads
   "Needs Windows 11 22H2." and the window stays solid; under 22000 it reads "Needs Windows 11." (PT's text).
D7. **Material before colour, natively.** PT's order existed because Electron's `setBackgroundMaterial`
   rewrote the window colour. In Flare the "colour" is the Slint side: `Theme.window-clear` (the window's own clear
   colour, PT's `setBackgroundColor`: solid ground, or transparent under glass) and the translucent ground tokens.
   The rule is the same words with a stricter meaning: going glass calls the backdrop FIRST and only then lowers the
   UI's ground alpha and makes `window-clear` transparent; leaving glass raises the UI to opaque FIRST and only then
   removes the backdrop. So no frame ever shows a translucent ground without a backdrop behind it (`order_for`,
   Task 25; the recorded call sequences in Tasks 17 and 25).
D8. **The window is created transparent whenever glass could ever be used**: GPU renderer effective AND
   `system_backdrop_ok`. It cannot be changed later (Verified facts). The ground is opaque (alpha 255) until
   the slider moves, so a transparent surface looks identical to an opaque one.
D9. **Theme state lives in `flare-settings::look::LookStore`** over M3's `PrefStore`, keys `flare.term.theme`,
   `flare.term.custom` (JSON, PT's shape), `flare.term.seeThrough`, `flare.term.font`, `flare.term.fontPct`,
   `flare.term.agentIndicator`, `flare.term.agentColor`, `flare.term.agentDoneColor`,
   `flare.term.agentQuestionColor`, `flare.window.background`, `flare.window.accent`, `flare.window.secondary`,
   `flare.window.customColours`, `flare.window.edges` (PT's `prism.*` names with the prefix changed, O10).
   The editor's draft is memory only. The switches (done, question, rainbow, failed, hooks) are M6/M7's.
D10. **A Custom with a sixteen-colour entry missing** (older or hand-edited saves; the editor always writes all
   sixteen) draws that slot in `pt-default`'s colour for it (PT drew xterm.js's own default there). Tested,
   recorded in `docs/features.md`.
D11. **A terminal face is the first installed face of its stack** for the whole grid (cell metrics need one
   face); per-glyph fallback (CJK, emoji) is cosmic-text's, as in M1. A stack with no installed face falls to the
   first monospace face on the PC, quietly.
D12. **Chrome tokens stay Prism Terminal's strings** (`"--p-accent": "#rrggbb[aa]"`) inside `flare-theme`, so a
   fixture compares as text; `chrome_apply` parses them once into `slint::Color`s. The Slint property for

//! Number helpers that behave like JavaScript's where Prism Terminal's code relies on it.

/// `Math.round`: a tie goes toward +infinity (Rust's `f64::round` sends it away from zero).
pub fn js_round(x: f64) -> f64 {
    let f = x.floor();
    if x - f >= 0.5 { f + 1.0 } else { f }
}

/// `Math.min(hi, Math.max(lo, n))` for a number that is not NaN.
pub fn clamp(n: f64, lo: f64, hi: f64) -> f64 {
    hi.min(lo.max(n))
}

/// Two lower-case hex digits of `n`, clamped to 0..=255 and rounded: PT's `byte` and `c` helpers.
pub fn hex_byte(n: f64) -> String {
    format!("{:02x}", js_round(clamp(n, 0.0, 255.0)) as u32)
}

optional `#`, then 3, 4, 6 or 8 hex digits (3 and 4 expand by doubling each digit; the 4th/8th is alpha / 255). Else

accepted where the caller passes a scale: alpha 0.01, rgb channel 2.55, hsl s/l 1). Alpha outside 0..1 or junk ->

0..100, hue wraps `((h % 360) + 360) % 360`, result via `hsl_to_rgb`. `alphaText(a)` = `Number(clamp(a,0,1).toFixed(2))`
printed with Rust `{}` (0.5 -> "0.5", 1 -> "1", 0 -> "0"); use `js_round(a * 100.0) / 100.0`. hsla format:
