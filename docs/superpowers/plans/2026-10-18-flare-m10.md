## Global Constraints

Copied from the roadmap and M2 to M9; every task obeys them.

- Windows 10 1809+ / 11, x64 only. Proprietary licence. **No em-dashes.** Flare's own names only (`names.rs`).
- **Every display scaling works**: 100, 125, 150, 175, 200, 225, 250, 300 percent, both renderers, and moving the
  window between monitors of different scalings. Every UI test in this milestone that has a pixel or geometry
  assertion runs at all eight scales (`SCALES` in `ui_harness.rs`), not at 100 and 225 only.
- **The e2e runs offscreen, unfocusable, never takes the foreground, one profile per scenario, reaps its processes,
  saves and restores the real clipboard (it never touches it: the app's clipboard is the in-memory stand-in under
  `--e2e`, and the guard compares the OS clipboard sequence number), opens nothing outside the app.**
- **Main never waits on the disk or a process** (rule 34): the hook's UI-thread handler never blocks; every blocking
  call in `flare`, `flare-win`, `flare-diag`, `flare-update` or `flare-term` carries `// sync-ok: <reason>`. The
  hook server thread and `tools/e2e` are test code and may block.
- The updater stays switched off (M9 D1). The dictation lines stay open (M8 is after this milestone).
- CI on every PR: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo nextest run
  --workspace`, `cargo deny check`. The e2e (`cargo run -p flare-e2e --release`) needs this machine (GPU, a real
  desktop session, installed Prism Terminal for the perf baseline), so it is the local PR gate, not a CI job.
- A new dependency adds its line to `README.md` and its entry to `THIRD-PARTY-NOTICES.md` in the same PR.
- Builders: Sonnet where marked, otherwise Haiku. Reviews: Opus. Never Fable.

## Review Focus

- **The hook cannot be reached without `--e2e`** (Tasks 7, 8): no pipe is created, no handler registered, no probe
  answers; the pipe has a current-user-only DACL and `FILE_FLAG_FIRST_PIPE_INSTANCE`; a second `--e2e` launch on the
  same profile cannot take the pipe over. Opus reads `e2e_hook.rs` and `e2e_glue.rs` end to end.
- **The e2e never takes the foreground and never touches the owner's world** (Tasks 8, 14): parking, the no-activate
  style, `GetForegroundWindow` before and after every scenario, the OS clipboard sequence number before and after the
  whole run, reaping by profile path only, a test that the reaper spares a process whose command line lacks the path.
- **A ported scenario keeps every assertion of its Prism Terminal original** (Tasks 16, 20 to 39): the number of `ok(`
  calls per scenario is in Appendix B; a scenario file whose `ctx.ok` count is below the original's lists each dropped
  assertion with its reason in a `// DROPPED:` comment, and the ledger (Task 74) counts them. An assertion that passes
  trivially (a probe that always returns true) is a defect: every probe has a test that makes it return the other answer.
- **The performance numbers are honest** (Tasks 60, 61, 70): Flare and Prism Terminal measured the same way on the same
  PC the same day; what is counted is written down (Decisions D5); a miss is reported as a miss.
- **The selection fix does not change what copy returns** (Task 19): every existing selection and copy test still passes
  unchanged; the new tests pin the redraw case.
- **DPI** (Tasks 9, 71, 72, 73): the live window really receives a DPI change through winit; the grid dimensions, the
  swapchain size and the hairline widths follow it; no frame is lost, no crash, the prompt line survives.

## Decisions taken by the planner (not the owner)

**D1. The test hook is a named pipe in the app, under `--e2e` only.** Not UI Automation (Slint's accessibility tree is
too thin for pixel and geometry assertions), not synthetic OS input (it goes to the foreground window, which the e2e
must never be), not Slint's `i-slint-backend-testing` (it replaces the backend, so the real winit window, the real
swapchain and the real DPI path would not be under test). The pipe carries typed JSON requests (Task 6). Why a pipe and
not M9's command file: request and reply in one round trip, no polling lag, and a reply that carries pixels' answers.
M9's file seams (`update-state.json`, `update-command`) keep working; the update scenarios use them as M9 defined them.

**D2. Keys are injected at the same seam the real key path ends in.** The real path is winit event, then the
window's event filter, then `keymap::key_event_from_parts`, then `AppCtl::on_key(&KeyEvent)`. The hook builds the
`KeyEvent` from a chord string (`"Ctrl+Shift+T"`, `"Enter"`, `"KeyC"`) with the same field rules (Task 8) and calls the
same function the filter calls (Task 8 refactors the filter closure body into `window::handle_key` if it is inline, and
a scan test asserts the filter does nothing else). What this does not test: winit's decoding of real scan codes. That is
covered by `keymap.rs`'s own tests (a winit `KeyboardInput` to `KeyEvent` table) and by the owner's hands.

**D3. Pointer and focus events go through Slint's `Window::dispatch_event`**, the same entry winit feeds. Resize goes
through `Window::set_size`. A DPI change is a real `WM_DPICHANGED` posted to the window's HWND, which winit turns into
`ScaleFactorChanged` plus the suggested resize (Task 9 proves this against winit 0.30 before anything depends on it;
fallback written in the task).

**D4. Parked at -32000, -32000**, not -4000: a monitor can sit left of or above the primary on the owner's desk and -4000 might
be on it. The window is created inactive, skip-taskbar and `WS_EX_NOACTIVATE` already (M3); Task 8 adds the position.

**D5. What the performance numbers count** (the owner may overrule; recorded in `docs/performance.md`):
- *Shell:* `cmd` for every number that gets a bar (same on both apps, fast, deterministic); PowerShell 7 is measured and
  reported beside it, with no bar, because its own start-up (profile, PSReadLine) is not the terminal's.
- *Cold start to a usable prompt (B1):* `usable_ms = prompt_ms + echo_ms`, both measured INSIDE the app on one clock whose
  zero is the process creation time (`GetProcessTimes`, so the loader time before `main` counts; the moment `CreateProcess`
  returned): `prompt_ms` = the end of the first frame (see "frame" below) whose grid shows a cursor row ending with the shell's
  prompt suffix (`>` for cmd); `echo_ms` = from injecting one key (`x`) at that moment to the end of the first frame that
  shows it (a prompt that does not take input is not usable). The harness queues the key before the prompt exists with
  `Request::KeyAtPrompt` (Task 6), so the harness's own polling never enters the number; it reads both values back from the
  probe `startup.trace`. The outside wall clock (harness `CreateProcess` to the probe answering) is reported beside it as a
  cross-check, not gated. Median of 7 launches after 1 discarded launch, each a fresh process in a fresh empty profile that
  already holds its first-run import marker. Prism Terminal measured the same way: zero = `process.getCreationTime()` read in
  Electron's main process; `prompt_ms` = the page's `Date.now()` in the first `requestAnimationFrame` after an xterm row ends
  with `>`; `echo_ms` = the page's key-to-render latency of one `x` (the B4 method). Both numbers are reported; the bar is
  Flare's alone (300 ms).
- *Frame:* on the GPU renderer, `BeforeRendering` (start, before the grid render) to `AfterRendering` of Slint's rendering
  notifier; on the software renderer (no notifier) the 16 ms `render_now` call (start to the grid image handed to Slint).
  Both apps are measured parked offscreen (the e2e rule); an offscreen window's present is not composed by DWM, so "frame"
  is the app's own render, never the compositor's. Written in `docs/performance.md` as a known limit.
- *Idle memory (B2):* private working set (Task Manager's "Memory (private working set)", read with the CIM class `Win32_PerfFormattedData_PerfProc_Process`, property `WorkingSetPrivate`, on both apps) summed over the app's process tree **minus** the shells and what they
  start (`cmd`, `pwsh`, `powershell`, `OpenConsole`, `conhost`, `node` agents), one tab at the prompt, 10 s after the
  first prompt, median of 3. Prism Terminal: the sum over `PrismTerminal.exe` and its Electron children (main, GPU,
  network, renderer, utility). Bar: Flare at most one third of Prism Terminal's.
- *Heavy-output throughput (B3):* `cmd /c type flood.txt` where the harness wrote a 100 MB file of 100-byte lines ending
  in `FLOOD-END`; the time from the Enter key to the first presented frame holding `FLOOD-END`. MB/s = 100 / seconds.
  Prism Terminal: the same command, time to `FLOOD-END` in xterm's active buffer. Bar: Flare at least twice Prism
  Terminal's MB/s, and on the GPU renderer **no presented frame over 33 ms** from 500 ms after the Enter until the end
  (frame = the interval between two presented frames while the window is dirty; `FrameStats` in `flare-render`).
  Software renderer: throughput at least Prism Terminal's, start at most Prism Terminal's, idle memory at most Prism
  Terminal's (the bar's "at least matches"); the 33 ms rule is measured and reported, not gated.
- *Keystroke latency (B4, planner bar):* in-process time from the key event entering `AppCtl::on_key` to the presented
  frame that holds the echoed character (Task 10 `Latency`), `cmd` at the prompt, 200 keys, 20 ms apart. Prism Terminal:
  in-page `performance.now()` from the `keydown` capture to xterm's `onRender` that contains the character. Bar: Flare's
  median at most Prism Terminal's median, and Flare's p95 at most 25 ms.
- *Scroll throughput (B5, planner bar):* 100,000 lines of output in the scrollback, then 5 s of wheel input at 1000
  events per second (the hook's `Wheel`); presented frames per second is at least 55 and no frame over 33 ms (GPU);
  Prism Terminal measured the same way and reported.
- *Idle CPU (B6, planner bar):* process CPU time (kernel + user) of the app tree minus shells over 10 s at a prompt, one
  tab, no agent: at most 0.5% of one core and at most Prism Terminal's. With one working agent mark animating: reported, bar 3%.
- *Frame time at 225% (B7, planner bar):* window 2250 x 1440 device pixels (1000 x 640 css at 225%) and 3840 x 2160, GPU
  renderer, during the flood of B3 and during a continuous window resize: render time per frame (build + submit, not the
  vsync wait) p95 at most 8.3 ms; presented-frame interval max 33 ms.
**D6. Every gated number is measured inside.** Start-up (from the process creation time), frame intervals, key-to-frame
latency and phase marks are inside the app (monotonic clock, read through the hook), so pipe jitter never enters a number;
the outside wall clock is reported as a cross-check only.
**D7. Prism Terminal's baseline is measured once per session on this PC** by Task 2 and stored in
`docs/perf/pt-baseline-<date>.json`; the bar file `docs/perf/bar.json` holds the rules (`flare <= pt / 3`), not copies of
absolute numbers, so a new baseline re-derives the bar.
**D8. A bar that is missed is a decision for the owner, not a quiet change.** If the GPU renderer's cold start cannot
reach 300 ms after Tasks 62 to 65 (the floor may be wgpu and Slint start-up, which the M4 spike measured at about 1.1 s
for the window), the report names the floor and the owner's choices (Q1). **What Task 65 can and cannot do:** a
`femtovg-wgpu` window presents nothing before Slint's own wgpu device, surface and femtovg pipelines exist
(`RenderingSetup`); the grid painter is Flare's and already switches between CPU and GPU (`host.rs` `GridPainter`,
`attach_gpu` in `RenderingSetup`). Painting the first grid frames on the CPU therefore removes only the GPU grid
painter's own set-up (`GpuPainter::new`: pipelines, shader compile, atlas) from the first frame; it cannot remove
Slint's floor. The phase `RenderSetup` (Task 3) makes that floor visible in every trace.
**D9. The difference register.** A parity line that Flare will not meet is not left open and not ticked: it becomes
`- [x] <line> DIFFERENCE DIFF-<n>: <what Flare does instead>. Rests on <O-number or Q-number or dated owner statement>.
Held by <test name>.` and gets a row in the "Deliberate differences" table of `docs/parity.md`. A difference whose only
basis is the planner's or a builder's call is written `PROPOSED` and listed in the PR description for the owner to confirm
or reverse (Q2). No difference is added silently.
**D10. A parity line is ticked only with a named test.** `- [x] ... (M10: <test_name>, <file>)`. The test must fail when the
behaviour is removed (the builder removes it once to see the red, per superpowers TDD) unless the line is a statement about
documents.
**D11. Hard tasks are Sonnet.** Marked in the task titles. Everything else is Haiku with exact signatures, files and values.

## Questions for the owner (none blocks the build; the PR description repeats them)

- **Q1 (cold start).** Task 65 builds what you asked for (M1 question 1): the first grid frames are painted on the CPU
  and the grid moves to the GPU when its painter is ready. If the GPU renderer still cannot reach 300 ms to a usable
  prompt, the remaining floor is Slint's own GPU window set-up (D8), and the choices are: (a) report the floor and accept
  it for the GPU renderer while the software renderer meets 300 ms; (b) start the whole window on Slint's software
  renderer (fast start, but see-through glass needs the GPU renderer, DIFF-5, and Slint cannot change a window's renderer

## Task 3: The start-up trace (crates/flare/src/startup_trace.rs; Haiku; needs Task 1)

**Why:** nothing today says where the 1257 ms goes. Every later start-up task is judged against these marks.

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub enum Phase { Main, Args, Backend, Component, Profile, ShellSpawn, RenderSetup, FirstFrame, FirstPrompt, Usable }
pub fn mark(p: Phase);                 // first call per phase wins; later calls are ignored; lock-free (AtomicU64 per phase, nanoseconds since process start)
pub fn since_process_start() -> Duration;   // GetProcessTimes creation time vs now (FILETIME), so it includes the loader time before main
pub fn snapshot() -> Vec<(Phase, Duration)>;  // in phase order, only marked ones
pub fn line() -> String;               // "startup: main 12 ms, args 13, backend 410, component 520, ..." for the log at `info`
```
`Phase::Usable` is marked by `AppCtl::on_key` when the first key reaches a tab whose grid already shows a prompt row (Task 1 inserts the call; the condition is `first_prompt_marked && !usable_marked`).
`FirstPrompt`: the first tick in which the front tab's grid has a non-empty row (term tick). `RenderSetup`: the end of the `RenderingSetup` arm (after `attach_gpu`; on the software renderer never marked). `FirstFrame`: the first `RenderingState::AfterRendering`, or on the software renderer the first `render_now` (the existing `first_software_frame` point).
These marks are for the log line and the phase table only; the gated B1 numbers `prompt_ms` and `usable_ms` are measured by the hook's `KeyAtPrompt` (Task 10) on the same clock (`since_process_start`) and appear in the same probe.

# WAVE 3: the parity sweep (M1 to M7 lines to zero)

## The sweep recipe (Tasks 40 to 47; Appendix A lists every line with the planner's expected disposition and the first place to look)

`docs/parity.md` is edited **one sweep task at a time, in the order 40 to 47** (one file, one writer at a time). The code and test work inside a task may use helpers, but the commit of a task contains its code, its tests, its `docs/parity.md` ticks and the new integer in `docs/parity-ratchet.txt`.
For every open line `L` in the task's slice:

1. **Read** the line, the Prism Terminal source it cites (`PT/...`), and the bracket note after it (`(open: ...)`, `(M3: ...)`): it says what the earlier milestone did and did not do.
2. **Find the test.** Search for the names in the note and for the behaviour (`grep -rn` in `crates`, `ui_tests`, `tests`). Run it. A test that passes but cannot fail (asserts nothing about the line) does not count.
3. **Disposition** (exactly one):
   - **A, held:** the behaviour is built and a test holds it. Tick: `- [x] <line> (M10: <test_name>, <path>)`; several tests are listed with commas.
   - **B, test missing:** the behaviour is built, no test. Write the test (at all eight scales when it measures geometry or pixels, `SCALES` in `ui_harness.rs`), run it, break the behaviour once to see it red (do not commit the break), then tick as A.
   - **C, behaviour missing:** write the failing test first, implement when the change is at most 40 lines in one file and has no design choice; otherwise write `NEEDS-SONNET: <line number> <one sentence> <files>` in the task report and leave the line open with `[M10-OPEN]` appended (the orchestrator turns it into a task in the defect pass; Task 47 refuses to finish while any `[M10-OPEN]` is left).
   - **D, difference:** the line cannot or should not be met. Follow D9: tick with `DIFFERENCE DIFF-<n>`, add the row to the register, name the basis (an `O<n>` or `Q<n>` decision, or a dated owner statement); `PROPOSED` when the basis is only a planner or builder call.
   - **E, held by an e2e scenario:** tick only after that scenario passes (the orchestrator tells the task which have): `(M10 e2e: <scenario>, tools/e2e/src/scenarios/<file>.rs)`.
   - **F, deferred to M8:** dictation. Append `[M8]` and leave open. Nothing else may be deferred.
4. **Never weaken a line to tick it.** If the line says 28 px and Flare draws 27, Flare is wrong (Disposition C) unless the line becomes a recorded difference.
5. **Report** a table `line | disposition | test or DIFF id`, the ratchet integer before and after, the tests added, and every `NEEDS-SONNET`.

## Task 49: Copying a big selection off the UI thread (crates/flare-term/src/{emulator,handle}.rs, crates/flare/src/{clip_flow,term_ui}.rs; Sonnet; needs Task 48; last of the wave 1d chain)

**Measured:** copying a 10,000-line selection takes about 47 ms on the UI thread (`term_ui.rs` calls `tab.handle.with_emu_quiet(|em| em.sel_text())`, i.e. `sel_text` under the emulator's `FairMutex`). The clipboard WRITE is already on a worker (`clip_flow::copy_async`); the cost is the READ. **Moving the same one-piece read to a worker is not enough:** it would hold the `FairMutex` for 47 ms, and the UI thread's next `snapshot()` (every frame) and the pty reader would wait behind it, so the window would still stall. The worker therefore reads in chunks and lets go of the lock between them.
```rust
pub const SYNC_COPY_ROWS: usize = 200;                         // a selection of at most this many rows is read inline, as today
impl Emulator { pub fn sel_text_rows(&self, rel: std::ops::Range<usize>) -> (String, bool /* the last row soft-wraps into the next */); pub fn sel_row_count(&self) -> usize; }   // rows counted from the selection's CURRENT first row, so a scroll or trim between two chunks (alacritty rotates the selection) moves nothing under the reader
impl TermHandle { pub fn selection_text_async(&self, done: Box<dyn FnOnce(Option<String>) + Send>); }
```
`selection_text_async`: a worker locks, reads `CHUNK_ROWS = 250` rows with `sel_text_rows`, unlocks, repeats, joining the pieces with the same newline-or-not rule `sel_text` uses (a soft-wrapped row joins without a newline), and calls `done(Some(text))`; if the selection changed between chunks (a new selection, a clear, alt screen: compare a selection generation counter the emulator bumps on every selection change; alacritty's rotation on scroll is not a change), it stops and calls `done(None)` (nothing is copied, no badge). `clip_flow` copies inline when `sel_row_count()` is at most `SYNC_COPY_ROWS`; otherwise `selection_text_async`, whose `done` posts back with `slint::invoke_from_event_loop` to write the clipboard and raise the Copied badge (rule: raised only by a successful copy). The text is what the selection covers when the worker reads it, normally within milliseconds of the press (xterm reads synchronously at the press; the difference only shows if the program rewrites the selected cells in those milliseconds: documented in `docs/features.md`). A second copy supersedes an unfinished first (a copy generation counter: the stale `done` is dropped). Ctrl+C with a selection is a copy and not the interrupt even while the copy is in flight. The small-copy path is byte-identical to before.
